Когда проектируешь таблицу, не спрашивай сначала:

«Какие поля сюда положить?»

Сначала спрашивай:

«Что представляет собой эта сущность и что с ней происходит?»

Например:

Device

Это конкретное физическое оборудование, установленное на объекте.

Что с ним происходит?

установили
обслужили
починили
заменили
сняли

Ticket

Это обращение клиента по проблеме/работе.

Что с ним происходит?

создали
назначили инженеру
взяли в работу
решили
закрыли
отклонили

Отсюда появляется история статусов.

Скорее сейчас у тебя есть привычка начинать проектирование с полей, а нужно учиться начинать с:

объекты → сценарии → события/изменения → правила → связи → данные.

Ты выполнила:
SCAN 0 MATCH *queues* COUNT 100

и получила:

1) "0"
2) 1) "laravel-database-queues:default:notify"
   2) "laravel-database-queues:default"

   Что означает 1) "0"
Это не найденный ключ.
SCAN работает порциями и возвращает два результата:

1) "0"       ← cursor (курсор)
2) (...)     ← найденные ключи

То есть:
- "0" — Redis говорит: «сканирование закончено, больше ключей искать не надо».
- второй пункт — список найденных ключей.
Если бы Redis вернул, например:

1) "17"
2) (...)

это означало бы: «я нашёл часть, продолжи SCAN с курсором 17».
У тебя 0, поэтому всё хорошо — найденный набор закончен.

Laravel
  │
  │ TestRedisJob::dispatch()
  ↓
Redis
  │
  └── laravel-database-queues:default
          │
          └── [ TestRedisJob ]

dispatch() не выполняет Job сразу. Он кладёт её в Redis.
А отдельный процесс:
php artisan queue:work redis
потом забирает её из Redis и выполняет.
